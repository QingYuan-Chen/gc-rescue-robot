# 工程规范

版本：V1.6。日期：2026-10-15。适用于本仓库新增及逐步迁移的代码。

目标是让每个模块位置明确、构建方式一致、接口含义清楚、验证结果可追溯。当前从最小运行基础开始，沿用 [重构方案](智能救援机器人重构方案.md) 的实施顺序。原工程问题整改不在本轮范围内。

本规范的核心要求：中文注释、高内聚低耦合、单一职责、方案替换同步清理，以及 `develop` 增量开发、审核后提交、`main` 稳定集成。

## 1. 目录与职责

| 位置 | 职责与修改规则 |
| --- | --- |
| `firmware/stm32/Core/` | CubeMX 启动、时钟、外设初始化和中断入口；用户接入代码放在生成器保留区 |
| `firmware/stm32/Drivers/`、`Middlewares/` | STM32 HAL、CMSIS、FreeRTOS；保持原许可证与格式，不混入业务代码 |
| `firmware/stm32/gc_rescue/` | 尚未替换的原工程参考实现；对应模块被新方案接管后，同步移除已废弃部分，来源通过 Git 历史与迁移记录追溯 |
| `firmware/stm32/App/` | 新增重构模块；文件随实际阶段创建，不预建整套空框架 |
| `vision/maixcam/` | MaixCAM 采集、识别与通信；设备路径、模型和参数从配置读取 |
| `hardware/` | 已确认接线与硬件资料 |
| `docs/validation/` | 各阶段的验证输入、结果、固件标识及未完成项 |
| `tests/`、`tools/` | 出现实际需要时添加离线逻辑测试和开发脚本 |
| `build/` | 唯一约定的生成产物根目录，不入 Git |

`App/` 内按职责分层，与重构方案一致：

```text
App/
  robot_app.c/.h  初始化与任务接入
  bsp/           引脚、定时器、编码器、串口和执行器底层接口
  runtime/       基础运行状态和周期观测
  control/       PID、速度环、转向环和底盘基础运动
  protocol/      帧编解码与协议字段定义
  perception/    视觉结果快照与坐标解释
  mission/       赛题状态机和动作顺序
  safety/        当前硬件支持的停车、超时和故障处理
  config/        板级映射、控制参数和任务配置
```

任务层调用控制或设备接口，控制层通过 BSP 操作硬件；BSP 不反向调用任务状态机。PID 计算与协议解析保持可独立运行，不直接包含 HAL 或 FreeRTOS。每个电机/舵机只有一个模块负责最终写入输出，其他模块提交命令，不跨层写 CCR 或 GPIO。

模块遵循高内聚、低耦合和单一职责原则：一个模块或源文件围绕一项明确职责组织，相关状态由该模块封装。模块间通过必要的公开接口与数据结构协作，不直接访问对方内部状态，不引入循环依赖，也不靠不断扩大的全局结构体传递所有业务数据。

职责拆分以变化原因和依赖关系为依据。驱动、控制算法、通信解析与任务决策分别组织；`robot_app.c` 只负责初始化和任务装配，不能堆积各模块实现。一个文件出现多个独立变化原因时，应拆分职责；不设机械行数上限，也不为缩短文件而增加无意义的转发层或碎片文件。

CMake 新模块使用显式源文件列表和 `target_*` 配置，避免目录里新增测试文件后被递归扫描进固件。方案替换和旧代码退出遵循第 6 节。

## 2. 语言、编码和格式

- 新 STM32 业务代码使用 C11，延续现有 HAL 与 FreeRTOS；当前不引入新的语言或任务框架。
- 新增代码和文档使用 UTF-8 无 BOM、LF 换行；C/Python 缩进 4 个空格，JSON/YAML 缩进 2 个空格。C 代码目标行宽 100，花括号独占一行。
- 文件、函数、变量和结构体字段使用 `snake_case`；类型使用 `module_name_t`；宏与枚举常量使用 `MODULE_NAME`。
- 公开函数带模块前缀，例如 `motor_set_duty_permille()`、`encoder_read_delta_counts()`；仅模块内使用的函数和状态声明为 `static`。
- 头文件写公开接口、类型及必要常量，使用 `ROBOT_MODULE_NAME_H` 形式的保护宏；不定义全局变量，不使用保留的双下划线名称。
- 项目自有代码、配置和脚本的新增或修改注释统一使用简体中文；仅保留必要的技术术语、缩写、专有名词及代码标识符，如 PID、DMA、HAL、FreeRTOS。首次使用容易产生歧义的术语时补充中文说明。
- 注释重点说明设计意图、约束、单位、调用条件和参数来源，并随实现同步更新。禁止保留与现有行为不符的注释、整段被注释掉的废弃实现，避免仅复述代码表面含义。
- 文件名和代码标识符继续遵循英文 `snake_case` 等命名约定；第三方版权声明、许可证及生成器固定内容保留原文。
- 使用 `.editorconfig` 和 `.clang-format`，格式化只作用于本次修改的新模块。

旧 `gc_rescue/` 中存在 GB18030 编码，与 UTF-8 文件混合。保持原文件编码，不按目录统一转码。`.editorconfig` 对旧业务、CubeMX 和第三方目录取消强制设置，`.clang-format-ignore` 排除这些目录；确需迁移单个文件时，明确记录编码转换并检查中文内容。不对整个仓库执行格式化或 `git add --renormalize .`。

## 3. 接口、参数和任务

接口名称体现物理量及单位：

| 含义 | 新接口约定 |
| --- | --- |
| 时间 | `period_ms`、`pulse_us`；算法积分时间使用 `dt_s` |
| 开环电机命令 | `duty_permille`，有符号千分比，范围 -1000…1000；正值表示该轮推动车体前进 |
| 编码器反馈 | `delta_counts` 为每个明确采样周期的有符号增量；正值对应轮子前进方向 |
| 底盘物理量 | `speed_m_s`、`yaw_rad`、`yaw_rate_rad_s`，在进入物理控制接口时换算 |
| 舵机 | 使用 `pulse_us` 或有定义的姿态枚举；业务层不传定时器 CCR 原始计数 |

原 PID 等效移植阶段同时保留了参数、周期、单位、方向、限幅和状态更新，结果保存在 [PID 迁移对照](PID迁移对照.md)。2026-10-15 用户确认重新设计车轮 PI：输入仍为 counts/10 ms，输出统一为占空比千分比，积分显式使用秒，并按实际限幅及换向输出回算；详见 [PI 控制设计](车轮PI控制设计.md)。旧 CCR 参数不能直接作为新参数使用。后续其他模块的等效迁移和算法改进继续分别留档。

车轮 PI 参数尚未整定，左右 Kp/Ki 上电默认均为零。调参固定使用 C 左轮，由用户按已确认的 [VOFA 方案](VOFA左轮调参.md)亲自操作。UART5 在线增益先编辑、整组应用，再回读实际生效值，Kd 未启用且非零设置拒绝；数值参数支持冒号或空格分隔。目标速度独立设置，闭环显式开始后持续运行，结束时主动停车；开环检查仍限时；不自行转轮、自动调参或把左轮结果直接复制为右轮已验证参数。

板级引脚映射集中在 `App/config/`，每个参数只有一处定义。控制参数按模块分组，写明来源、单位与当前状态；实验参数不得作为已验证默认值悄悄合入。当前接线为 C 左轮、D 右轮、Servo1 夹爪、Servo2 云台；业务接口使用 `left/right`，不以端口字母命名左右轮。端口变更时同步核查初始化、故障停机、工具及文档，原接线的实测记录保留为历史依据。电机输出方向与编码器反馈方向分别校准，不能因电机取反就推定编码器也应取反。

周期控制任务使用固定周期调度，记录周期与采样时刻；普通任务通过等待、队列或延时让出 CPU。中断只做必要的数据收发、计数和事件通知，解析与控制放到任务中。任务间共享数据明确生产者与消费者，用队列、临界区或快照交接；`volatile` 不作为同步机制。停止命令经过输出所有者执行并清理该控制层需要清理的状态。

阶段 4 起的底盘行为以 [底盘控制规则与比赛动作](底盘控制规则与比赛动作.md) 为统一约定：闭环目标经过正、零、负值时保持 PI 状态；显式停车、开环命令到期或退出控制时归零输出并清理状态，持续闭环不设到期停车。零速度目标、零输出、反馈停稳和任务成功分别判断。模式切换、比赛动作及异常恢复的设计状态与已实现能力必须分开记录，尚未实测的检测阈值不能写成有效保护。

## 4. 统一构建与 CLion

当前验证工具组合为 CMake 3.28.1、Ninja、ARM GCC 13.3.1，来自 STM32CubeCLT 1.20.0。升级工具链单独验证。工程使用 ARM 编译器，不为同一固件启用 MinGW 或 Visual Studio 编译配置。

共享入口为 `firmware/stm32/CMakePresets.json`：

| 预设 | 输出位置（相对仓库根目录） | 用途 |
| --- | --- | --- |
| `stm32-debug` | `build/stm32-debug/` | 默认开发与逐项上板验收 |
| `stm32-release` | `build/stm32-release/` | 优化构建；不能用 Debug 的运行结果替代其验收 |

命令行在 `firmware/stm32/` 执行：

```powershell
cmake --preset stm32-debug
if ($LASTEXITCODE -ne 0) { throw 'CMake 配置失败' }
cmake --build --preset stm32-debug --parallel 8
if ($LASTEXITCODE -ne 0) { throw '固件构建失败' }
```

CLion 打开 `firmware/stm32/`，配置名为 `STM32` 的工具链：CMake/Ninja 使用 STM32CubeCLT，C/C++ 编译器分别为 `arm-none-eabi-gcc`、`arm-none-eabi-g++`，调试器使用 `arm-none-eabi-gdb`。这些工具所在目录加入本机 PATH，绝对安装路径留在 IDE 设置中。使用 Debug Servers 时，其 Debugger 项也应显式选择 `arm-none-eabi-gdb`；该项独立于工具链，不能仍选内置 Windows GDB。烧录恢复与配置验证见[2026-10-16 记录](validation/2026-10-16-vofa-flash.md)。

加载预设后启用 `stm32-debug` 对应的配置，关闭重复的手工 Debug/MinGW 配置。已有打开的 CLion 窗口可能需要重新加载并启用新预设；新增预设文件不等于 IDE 已自动切换。[CLion 官方说明](https://www.jetbrains.com/help/clion/cmake-presets.html)解释了预设与工具链的关联及启用方式。

本机个性化设置写入不跟踪的 `CMakeUserPresets.json`，共享 `CMakePresets.json` 不写用户盘符。新预设必须实际存在，不手工填入不存在的 `--preset` 名称。现有 `cmake-build-*` 与旧 `build/stm32/` 仅保留为历史产物，不再作为默认入口，也不在本次整理中删除。

CubeMX 变更先修改 `.ioc`，生成后审查差异；手写接入代码使用 `USER CODE` 保留区或独立模块。生成器模板不能直接覆盖当前有效的 CMake 入口；涉及生成流程时须连同用户模块注册和编译选项一起验证。

## 5. 验收要求

重构按“最小运行基础 → 车轮开环/编码器 → 原 PID → 速度环 → 转向环 → 外设基础 → 任务 → 视觉与执行机构协同”推进。每次只接入本阶段需要的模块。

| 变更 | 必须验证的内容 |
| --- | --- |
| 文档或格式配置 | 内容一致性、链接、规则是否误伤旧文件 |
| 构建配置 | 预设可解析、CMake 可配置、对应固件可编译 |
| PID、解析和单位转换 | 有价值的离线输入/输出对照，再按依赖进入实车验证 |
| GPIO、PWM、编码器、舵机 | 对应硬件上的明确指令、实际输出/反馈与停止行为 |
| 控制环或组合动作 | 固定测试输入、反馈记录、重复运行结果 |

验证记录写明：代码提交或差异、工具链/预设、固件 SHA256、接线与供电条件、测试输入、预期和实际结果、通过/待验证项。编译、烧录校验和硬件运行分别记录；上板测试前说明是否需要执行器供电。当前阶段没有实测的项目如实标记，不能推断为通过。

## 6. 方案演进与旧实现清理

方案变更采用替换式重构，并在变更生效时同步清理。确认新方案接管某项职责后，应在同一批变更中完成：

1. 按新职责与接口组织实现，更新全部调用方和数据流，保证执行入口唯一。
2. 删除被替代的函数、文件、分支、配置项和无效依赖，同步调整 CMake 源文件列表。
3. 更新相关测试、注释、接口说明和当前方案文档，移除已失效的默认参数与使用说明。
4. 搜索旧接口和配置的引用，检查是否存在遗漏；完成与改动相称的构建及功能验证。

不以层叠条件判断、遗留兼容分支、重复实现或 `#if 0` 堆叠新方案，不在工作源码中长期保留 `*_old`、`*_backup` 等旧方案副本。发现原有结构不再适配新方案时，重新划分职责并替换相关实现，避免连续补丁掩盖设计变化。

正常的小幅迭代按实际影响修改，无需每次全量重写。清理范围限定为已经被替代或确认废弃的部分；尚未迁移且仍有依赖的模块继续保留。历史方案与恢复依据由 Git 历史、迁移说明和已有本地归档保存，同级原工程 `../gc_rescue/` 的备份不属于重构工作树中的清理对象。

## 7. 分支管理与增量提交

| 分支 | 定位 | 提交与集成规则 |
| --- | --- | --- |
| `develop` | 日常开发与阶段集成 | 功能实现、重构、构建配置和文档更新在此推进；每完成一个边界清楚、可检查的工作增量，先向用户提供差异及检查结果，审核确认后再提交 |
| `main` | 稳定版本 | 仅合入从 `develop` 验收通过的阶段版本，不直接用于日常开发和未验证实验 |

提交粒度以独立改动为单位，不必等待整个重构阶段全部结束，也不将多个无关功能混入一次提交。每次提交说明改动目的、范围和验证结果，例如 `docs: 明确注释、模块职责与分支规范`、`build: 增加 STM32 预设`、`feat(motor): 实现左轮开环输出`。

`develop` 的固件提交应保持可构建，完成当前能够执行且与改动相关的检查；需要硬件而尚未实测的增量，可以在用户审核确认后提交，并明确标记“待上板验收”，但不能因此认定为稳定版本。纯文档和配置规范按对应检查验收，不要求无关的硬件测试。

稳定版本合入 `main` 前，应满足当前阶段与本次改动的验收要求：相关构建与测试通过，涉及硬件行为的部分已有对应实测，已替代的实现清理完成，文档与验证记录一致，且没有阻断本阶段能力的已知问题。稳定范围以已实现的阶段为准，不要求提前完成整车全部功能。

合并保留 `develop` 的提交历史，允许快进或常规合并，不通过强制推送覆盖 `main`。本地提交、远端推送与稳定版本合并是不同操作，均遵循当前用户授权；完成修改和验证后先提供可审核结果，不自动执行 commit、push 或合并 `main`。用户已要求保留的已有提交不回退、不重写。确需隔离并行功能时再使用短期功能分支，完成后回到 `develop` 集成。

源码、配置、原理图和验证文档进入 Git。缓存、机器设置、完整 Flash 备份、模型权重与数据集不进入普通提交；固件发布有需求时另附发布产物。保留原工程和历史备份，不为了目录整齐丢失可追溯依据。
